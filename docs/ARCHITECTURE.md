# Архитектура проекта

Этот документ объясняет, **как устроен код и почему именно так** — чтобы
при следующей правке (в том числе от преподавателя) было понятно, что где
менять, и не пришлось переписывать всё заново.

## Главная идея: данные отдельно от кода

Самое важное требование к проекту — то, что уровни, типы мини-игр и баланс
будут часто меняться. Если бы уровень 1 был "зашит" в код (конкретные
числа, конкретная сцена), любое изменение требовало бы трогать C#-скрипты
и пересобирать проект. Вместо этого используется подход **data-driven**:

- Код умеет **выполнять** мини-игру любого зарегистрированного типа (бой с
  големами, двери, ...), но не знает заранее, сколько уровней в игре и что
  на них происходит.
- Все конкретные числа и последовательности живут в **ассетах** —
  Unity-объектах типа `ScriptableObject`, которые редактируются мышкой в
  инспекторе Unity, без единой строчки кода.

Практически это значит: **новый уровень = новый ассет**, а не новый код.
**Новый тип мини-игры = новый класс, который реализует общий интерфейс**, —
остальной код (меню, прогресс, экран выбора уровня) его не касается и
менять не нужно.

## Карта кода (`Assets/_Project/Scripts/`)

| Папка | Что тут живёт | Зависит от |
|---|---|---|
| `Data/` | Описание "формы" данных: определения уровня, мини-игр, настроек | ни от чего (это фундамент) |
| `MathGen/` | Генератор математических примеров | `Data/` |
| `Services/` | Сохранение настроек и прогресса на диск | `Data/` |
| `Minigames/Framework/` | Общий "контракт" мини-игры (`MinigameController`) | `Data/` |
| `Minigames/Towers/` | Мини-игра "Башни" | `Framework/`, `MathGen/` |
| `Minigames/Doors/` | Мини-игра "Двери" | `Framework/`, `MathGen/` |
| `Core/` | Игровой поток: какая сцена за какой следует, кто хранит выбранный уровень | всё вышеперечисленное |
| `UI/` | Экраны: главное меню, выбор уровня, настройки, HUD, пауза, результат | `Core/`, `Services/` |
| `Utils/` | Мелкие переиспользуемые вещи (например, простые анимации-твины) | ни от чего |
| `Editor/` | Инструменты только для редактора Unity (не попадают в сборку игры) | `Data/` |

Стрелка зависимости всегда идёт "в одну сторону": `UI` знает про `Core`, но
`Core` ничего не знает про конкретные экраны UI. Это и даёт гибкость —
можно переделать весь интерфейс, не трогая игровую логику, и наоборот.

**Одно осознанное исключение:** `GameplayController` (в `Core/`) напрямую
ссылается на три компонента из `UI/Gameplay/` — `GameplayHud`, `ResultPanel`,
`PausePanel`. Это не нарушение правила, а его уточнение: экраны *меню*
(главное меню, выбор уровня, настройки) — самостоятельные "страницы", про
которые игровая логика ничего не знает и знать не должна. А HUD/пауза/экран
результата — не отдельные страницы, а часть одной игровой сцены, и именно
`GameplayController` ей управляет. Общение при этом идёт только через
маленький публичный интерфейс каждого компонента (`ShowWin`, `UpdateTimer`,
события `ResumeRequested`/`ExitRequested`) — сами эти компоненты ничего не
знают про `GameplayController` в ответ, циклической зависимости нет.

## Как устроены данные уровня

```
LevelCatalog (один ассет — общий список игры)
 └── List<LevelDefinition>              (уровень 1, уровень 2, ... уровень N)
      ├── visualTheme: LevelVisualTheme  (фон/цвет — то, что "мрачнеет" от уровня к уровню)
      └── sequence: List<MinigameDefinition>   (обычно одна мини-игра на уровень)
           ├── TowerMinigameDefinition   (наследник MinigameDefinition)
           │    ├── towerSizes: [2, 3, 4]     — сколько големов в каждой последовательной башне
           │    ├── heroStartingPower
           │    └── controllerPrefab → префаб, который умеет всё это разыграть
           └── DoorMinigameDefinition    (наследник MinigameDefinition)
                ├── doorsPerRound: 4
                ├── correctDoorsRequired: 3
                └── controllerPrefab
```

`MinigameDefinition` — абстрактный базовый класс. `LevelDefinition.sequence`
это список именно базового типа, поэтому в него можно положить как
`TowerMinigameDefinition`, так и `DoorMinigameDefinition`, так и любой
будущий `КакойТоНовыйMinigameDefinition` — без изменения `LevelDefinition`.

**Практически:** чтобы добавить уровень 11 — создаёте ассет `LevelDefinition`
(правой кнопкой в `Project` → `Create → MathGame → Level Definition`),
задаёте тему и мини-игры, перетаскиваете в конец списка `LevelCatalog`.
Порядок в списке = порядок в экране выбора уровня и порядок разблокировки.
Чтобы убрать уровень — удаляете из списка. Чтобы поменять местами — меняете
местами элементы списка. Код при этом не трогается вообще.

## Как мини-игра на самом деле запускается

Все мини-игры подчиняются одному контракту:

```csharp
public abstract class MinigameController : MonoBehaviour
{
    public event Action Completed;
    public event Action Failed;
    public abstract void Begin(MinigameDefinition definition, MinigameRuntimeContext context);
}
```

`GameplayController` (живёт в сцене `Gameplay`) не знает, что такое "голем"
или "дверь". Он делает простую вещь по кругу:

1. Берёт следующий `MinigameDefinition` из `sequence` текущего уровня.
2. Создаёт (`Instantiate`) его `controllerPrefab`.
3. Вызывает `Begin(definition, context)` и подписывается на `Completed` / `Failed`.
4. Если `Completed` — переходит к следующему элементу `sequence` (или
   завершает уровень, если элементы кончились).
5. Если `Failed` — показывает экран поражения и перезапускает уровень.

Это и есть тот самый механизм, который позволяет **чередовать типы
мини-игр внутри одного уровня** и **добавлять новые типы**, не переписывая
`GameplayController`: он работает только с базовым контрактом `Begin` /
`Completed` / `Failed`, а не с конкретной реализацией.

### Как добавить новый тип мини-игры в будущем

1. Создать `НовыйTipMinigameDefinition : MinigameDefinition` (поля с
   балансом — свои для этого типа).
2. Создать `НовыйTipMinigameController : MinigameController` — реализовать
   `Begin(...)`, вызвать `RaiseCompleted()` / `RaiseFailed()` в нужный момент.
3. Собрать префаб сцены для этого контроллера, назначить его в поле
   `controllerPrefab` у ассета определения.
4. Положить ассет в `sequence` нужного уровня.

Ни `GameplayController`, ни экран выбора уровня, ни прогресс/настройки не
меняются.

## Генератор примеров и сложность

`IMathProblemGenerator.Generate(DifficultyContext)` — единая точка, которая
создаёт математический пример (`"3 + 2"`, ответ `5`) и для голема, и для
двери. `DifficultyContext` — это просто диапазон чисел и разрешённые
операции (сложение/вычитание/умножение/деление).

`DifficultyScaler.Build(settings, levelIndex)` — единственное место, где
"настройки + номер уровня" превращаются в конкретный `DifficultyContext`
(если в настройках включён рост сложности — верхняя граница диапазона чисел
растёт с номером уровня). Если преподаватель попросит другую формулу роста
сложности — меняется одна эта функция, а не код мини-игр.

## Сервисы: настройки и прогресс

`ISettingsService` / `IProgressService` — интерфейсы, реализации хранят
данные в JSON-файле в `Application.persistentDataPath` (стандартная папка
Unity для локальных данных пользователя, не связана с самим проектом).
Использование интерфейса, а не конкретного класса напрямую, — это задел на
будущее: если появится требование "сохранять в облако" или "экспортировать
прогресс", меняется только реализация, а весь остальной код (который
работает через интерфейс) не заметит разницы.

`GameServices` — один объект-"точка входа", живёт в сцене `Boot` и
переживает переход между сценами (`DontDestroyOnLoad`). Даёт доступ к
`Settings`, `Progress`, `ProblemGenerator` и `LevelCatalog` откуда угодно.
Это осознанно простой аналог Dependency Injection ("Service Locator") —
для проекта такого масштаба полноценный DI-контейнер был бы избыточным
усложнением.

## Сцены

Всего 3 сцены — не по одной на уровень:

- **Boot** — стартовая, поднимает `GameServices` и сразу переключается на `Menu`.
- **Menu** — главное меню, выбор уровня и настройки — это **один и тот же
  scene**, три панели внутри одного канваса, между ними переключается
  `MenuUIController`. Экран выбора уровня *не* хардкодит 10 уровней — он
  читает список из `LevelCatalog` и строит кнопки в цикле.
- **Gameplay** — тоже одна сцена на все уровни и все мини-игры. Какой
  именно уровень играть, передаётся через `LevelSelection` (простое
  статическое хранилище на переход между сценами) и разворачивается
  `GameplayController`-ом по данным `LevelDefinition`, как описано выше.

Меньше сцен — меньше дублирования настроек камеры/канваса/освещения и
куда легче что-то поменять во всех уровнях разом.

## Что нужно делать руками в редакторе Unity

Код (все `.cs`-файлы) можно писать и редактировать текстом. А вот:

- создание самих файлов сцен (`Boot.unity`, `Menu.unity`, `Gameplay.unity`),
- расстановка объектов на сцене и настройка канваса,
- перетаскивание ссылок в инспекторе (например, какой префаб голема
  использует `TowerMinigameController`),
- создание ассетов `ScriptableObject` (уровни, темы, определения мини-игр)

— это требует интерфейса Unity Editor и делается руками (drag-and-drop),
это фундаментальное ограничение Unity — такие вещи не хранятся как текст,
который можно надёжно сгенерировать снаружи. Пошаговые инструкции для
этих шагов даются в чате по ходу разработки.
